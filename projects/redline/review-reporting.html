Review output ​

Redline writes its review contract under REDLINE_OUTPUT_DIR/reviews/. The PR-level record is authoritative. Per-file records and the legacy run summary remain for inline publication, diagnostics, benchmark compatibility, and migration.

FilesPurpose
review.json, review.mdAuthoritative PR-level findings, coverage, limitations, and verdict
<fileId>.json, <fileId>.mdValidated per-file triggers, remediation guidance, and candidate diagnostics
verification/<fileId>.jsonOpt-in verifier dispositions and bounded, credential-redacted raw output; absent when no verifier ran
follow-up/<fileId>.jsonBounded action-owned requests, pinned provider identity, resolved head-source anchors, and explicit unavailable reasons
summary.json, summary.mdVersion-3 compatibility summary for existing benchmark/report consumers

The output travels in the <artifact-name>-reviews artifact. When a publication token is supplied, the publisher consumes review.json for the managed PR summary and the per-file records for diff-anchored inline comments.

PR-level record ​

review.json is version 2. Its top-level shape is:

json
{
  "version": 2,
  "base": "…full base commit…",
  "head": "…full head commit…",
  "findings": [],
  "synthesis": { "version": 1, "groups": [], "decisions": [], "budgets": { "fileReviews": 25, "inlineComments": 100 } },
  "rejectedCandidates": [],
  "coverage": {},
  "limitations": [],
  "verdict": {
    "status": "mergeable | mergeable-after-verified-fixes | human-decision-required | inconclusive | blocked",
    "reasons": []
  },
  "files": [],
  "legacySummaryVersion": 3
}

Each PR finding keeps exactly one changed-diff trigger through triggerFileId, triggerPath, side, startLine, endLine, and byte-identical evidence. A single finding can also carry:

  • multiple supportingEvidence locations at the exact base or head revision;
  • bounded provider-derived graphReferences;
  • a source- or graph-backed impactPath;
  • dimensions, classification, severity, and confidence;
  • behavioral contract, failure scenario, reachability, root cause, impact, blast radius, and reversibility;
  • assumptions, counter-evidence, and remaining uncertainty;
  • remediation guidance, a regression-test proposal, and explicit verification/remediation states.

This permits one cross-file finding without moving its publication anchor away from the authoritative diff.

Evidence validation ​

The trigger remains subject to the strict diff validator:

  • the file must be textual;
  • both span endpoints must be changed lines on the declared side;
  • evidence must exactly equal the trigger start line;
  • the classification must respect the configured finding scope.

Supporting source evidence is re-read from captured repository content. Head evidence resolves from exact-head source. Base evidence resolves from captured base files for every reviewed non-added file. Deleted and renamed paths remain captured even when review policy excludes them. The revision must equal the reviewed base or head commit, the path must be normalized and captured, the inclusive range must contain valid existing source lines, and its start-line evidence must match exactly. SourceEvidence.evidence contains only the anchor line: interior lines carry no claimed text, so validation confirms their location and bounds, not their contents or the causal interpretation of the range.

Graph references are provenance, not source authority. The discovery contract accepts them only when they carry the selected provider and exact version, the loaded base snapshot, the declared related-spans capability, a bounded query and relationship, and an action-produced SHA-256 digest from the source-resolved context. The artifact parser binds each query, relationship, resolution, and digest to its exact related span; the review validator then requires that digest to belong to the loaded fact set. A model-generated, self-consistent digest is rejected. Graph references never determine inline comment paths or line numbers. Current action-owned indexes are base-revision graphs; a claimed head graph snapshot is rejected rather than guessed.

Impact-path steps index either supportingEvidence or graphReferences. A complete path needs at least one valid step. Partial or unresolved paths require an explicit limitation.

Prompt source selection ​

Policy redline-file-review/v5 keeps the authoritative diff and replaces redundant whole-file payloads with revision-pinned source excerpts. For modified and added files, Redline selects changed head hunks with 16 surrounding lines and adds a bounded containing function, method, class, or Python declaration body when it can resolve one deterministically. The base side is not repeated for modified files because the authoritative diff already contains removed and context lines. Deleted files instead receive bounded base-revision excerpts and no head source. Every excerpt records its exact revision, path, inclusive line range, selection reason, original byte count, embedded byte count, and whether the full file was omitted. A source file is read only when it is a regular file inside the captured root, stays within the existing 128 KiB per-file input limit, and can produce at most 64 KiB of prompt content per side. The total untrusted payload keeps the existing 512 KiB limit.

Source-validated indexed context is included only when it contributes at least one related span. It remains bounded separately and cannot replace the authoritative diff or revision-pinned source.

Independent candidate handling ​

Harness output uses review-document version 4 under policy redline-file-review/v5. A version-4 document can include up to two candidate-indexed contextRequests when the trusted run declares action-owned follow-up with only incoming or outgoing directions; it cannot provide paths, queries, provider commands, or budgets. Versions 2 and 3 remain accepted for existing recordings. The reason field is required only for omitted: it must be nonblank and at most 500 characters. A reason on clean or findings is ignored because those outcomes are defined by candidate inspection, not an omission explanation. Candidates are parsed and validated independently. One malformed schema, invalid trigger, mismatched source location, unsupported provider claim, or bad graph digest produces a bounded rejectedCandidates entry; it does not erase unrelated valid siblings. Findings may share a changed trigger: exact duplicates collapse, while distinct category/title identities remain separate. Only claims with the same category/title identity and incompatible classifications or severities are rejected as conflicts. A rejected candidate is never published.

If every candidate fails, the file is omitted with invalid-output. Mixed valid and invalid candidates retain the valid findings while the rejected count makes required baseline coverage incomplete, preventing a clean verdict.

Raw model output remains a bounded diagnostic field in the per-file artifact. It is not part of the publishable finding contract.

The library runner also supports an opt-in independent verifier for benchmark evaluation. Each candidate-bearing file gets a fresh harness invocation using the configured model and a separate fixed redline-verification/v3 policy; clean files make no verifier call. Its timeout is 10 minutes per file. The parser accepts bare JSON or exactly one standalone JSON code fence, then applies the same strict schema and source checks. Prose around the fence, invented fields, or unsupported citations still fail closed. A publishable disposition must cite captured base/head source (the changed trigger may suffice). The verifier can select a new span from the reviewed file's captured base or head source, but review code re-resolves the exact revision, path, range, and start-line text before publication. Evidence from another file must be inside the source-resolved indexed context supplied to the verifier, already belong to the validated candidate, or come from an action-validated follow-up result. Malformed output or failed execution suppresses all of that file's candidates and records incomplete required coverage. Explicitly disproved or duplicate candidates are artifact-only but count as completed verification, not missing coverage. The file record includes candidate-verification counts and duration; the separate version-1 verifier artifact stores candidate IDs, dispositions, bounded reasons, and redacted raw output. Discovery raw output remains in the per-file record. The versioned discovery policy prohibits requests when the trusted run has no action-owned follow-up; it reviews from captured source and omits work it cannot assess. Unexpected requests with verification off still fail closed rather than publishing unverified claims. A permitted follow-up is converted to a fixed depth-one, fan-out-eight, result-eight request by review code. Only trusted action code may execute it against a matching pinned base graph: the worker checks reviewed file identity, provider/version, graph state, base revision, query limits, and captured head-source anchors. The review core revalidates returned anchors independently before the verifier can cite them. Per-file and cumulative request budgets, worker timeouts, malformed output, missing providers, and stale snapshots yield explicit incomplete required coverage; graph labels alone cannot confirm a finding. No model-controlled path or query reaches the provider. The GitHub Action and standalone CLI do not activate the verifier or this path: independent live-model quality and latency gates must pass first.

Coverage and limitations ​

Coverage facets use only these states: completed, incomplete, unavailable, and not-applicable. Absence is never treated as success.

The PR record states:

  • considered required files, omitted required reviews, and trusted-policy exclusions with one deterministic reason per file;
  • changed-symbol availability;
  • diff, base-source, head-source, and indexed-context retrieval;
  • required baseline specialist completion;
  • whether tests, contracts, schemas, and configuration were independently inspected;
  • selected code-intelligence provider, version, base/head snapshots, capabilities, cache state, and bounded diagnostics;
  • graph-query and impact-traversal status;
  • source-confirmed and provider-derived relationship counts;
  • provider disagreement, unresolved symbols, unsupported languages, and dynamic-behavior uncertainty;
  • truncation, finding, source-byte, and related-span budgets;
  • rejected candidates, opt-in verifier completion and explicit falsifications, action-owned follow-up completion, synthesis publication budgets and suppressions, remediation availability, and fix-verification availability.

Unavailable optional code intelligence is explicit but does not by itself make the run inconclusive. A trusted-policy exclusion is listed separately and never counted as a completed review or required omission. An omitted required file, invalid candidate, or inconclusive verifier makes required baseline coverage incomplete. A successful verifier falsification or deduplication is recorded but does not invalidate otherwise complete coverage.

Deterministic verdicts ​

The model cannot select the PR verdict. Redline derives it from validated findings and coverage:

  • blocked: at least one unresolved validated defect remains;
  • human-decision-required: unresolved evidenced risks, test gaps, design debt, or questions remain without a defect blocker;
  • inconclusive: required coverage is incomplete or a candidate failed required validation, and no stronger finding consequence applies;
  • mergeable-after-verified-fixes: findings remain in the record, but each finding and remediation is independently confirmed/verified;
  • mergeable: no validated findings remain and every required coverage facet completed.

Verified runs synthesize source-backed root-cause groups, retain every changed-line trigger, and choose a deterministic representative. They sort by severity, reversibility, source-evidence strength, and bounded confidence; model prose cannot set the rank or verdict. Incompatible source-backed contracts require human judgment. File-review (25) and inline-comment (100) budgets apply after ranking. Duplicate, conflict, unverified, and budget-suppressed findings remain in review.json/review.md decisions. Confirmed critical suppression adds a required coverage limitation; all suppression counts and bounded examples appear in the managed PR summary. The publisher uses only the saved plan and fails closed if a verified review has no plan.

The discovery stage accepts only verification.status: unverified and remediation status guidance or proposed. It cannot verify itself. The opt-in verifier can set confirmed source-backed findings; it cannot independently verify a proposed fix, and production execution remains disabled pending the benchmark gate.

Per-file records and remediation ​

Per-file records are version 4. Every record includes rejectedCandidates and rich findings. Each accepted finding receives:

  • an optional suggestion rendered from authoritative span content plus the model's bounded replacement text;
  • a deterministic fixPrompt that cites the validated location, evidence, impact, current source, and remediation guidance.

GitHub inline comments remain anchored only to the validated trigger. Supporting evidence, graph references, and impact paths explain the finding but cannot relocate publication.

Cross-run reuse telemetry ​

The GitHub Action can restore a version-2 PR-scoped review cache before it builds the worker queue. A per-file record is reusable only when its versioned semantic fingerprint matches the current fixed policy and schema, harness and model configuration, finding scope, timeout, authoritative diff, bounded revision-pinned source context, requirements, and resolved indexed context. Exact commit identifiers are normalized to base/head roles, then every restored finding is remapped and revalidated against the current revisions. Current synthesis, budgets, omissions, verdict, stale-head check, and publication are always rebuilt.

Per-file JSON and Markdown report execution: executed | reused. Reused records also report savedDurationMs, based on the prior validated execution. summary.json and summary.md include version-1 reuse telemetry: cache status, valid restored entries, invalid entries ignored, reused files, executed files, and estimated model time saved. They also include additive execution-budget telemetry: per-file and whole-run deadlines, elapsed review time, deadline status, and the number of files omitted by deadline exhaustion. Cache data retains bounded, already-redacted rendered suggestions so reused findings keep the same apply-able patch. It never includes prompts, raw model output, verification artifacts, credentials, or publication tokens.

Only clean and findings results are written to the cache. Omissions, harness failures, timeouts, invalid output, incomplete verification, and verifier runs that consumed the shared follow-up budget are excluded. Corrupt, oversized, stale, path-mismatched, or evidence-invalid entries degrade to normal review execution.

Compatibility and migration ​

Migration is explicit:

  • Harness review document version 4 adds bounded candidate-indexed follow-up intents; versions 2 and 3 remain readable.
  • Version-2 harness documents remain accepted during migration. Redline maps their validated fields into version 4 records and labels every unavailable rich field as legacy-derived or unresolved; it does not reinterpret missing evidence as completed analysis.
  • Per-file record version 4 adds the rich finding and rejected-candidate contract.
  • PR-level record version 2 adds optional synthesis and publication coverage. The publish-only loader migrates legacy version-1 non-verified records; it rejects a verified version-1 record before migration so the synthesis-plan check cannot be bypassed.
  • Run summary version 3 remains unchanged as a subordinate compatibility artifact; it gains optional additive trusted-policy exclusion records, reuse telemetry, execution-budget telemetry, per-file execution fields, and indexed-context cache, diagnostic-code, and stage-timing telemetry. Readers treat absent exclusion records as an empty legacy list.
  • Pull-request review version 2 retains the existing coverage.files.excluded path array and adds optional coverage.files.excludedDetails records with file ids and reasons.
  • Context-bundle manifest version 2 records strict eligibility-policy provenance plus exclusionReason for every non-reviewed file. Legacy version-1 manifests remain readable with a conservative legacy reason.
  • Review policy redline-file-review/v5 uses the fixed modules in prompts/v7/ with focused source-context payload versions 3 and 4. The full-file payload versions 1 and 2 remain available only for reproducible benchmark comparison. Earlier prompt policies remain archived for versioned recordings.

Fix execution and learning stages are not implemented. The follow-up worker and synthesis plan are implemented behind the verifier activation gate; they are not production quality claims.
