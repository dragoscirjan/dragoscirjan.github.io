GitHub composite action ​

github/action.yaml is a composite action. It builds the review context bundle for a pull request's exact base and head commits and, when review inputs are supplied, builds bounded indexed context, runs the harness review, and uploads its output as artifacts.

Inputs ​

Inputs are fixed enums and data. No input accepts free-form review instructions.

InputValuesNotes

Review execution is enabled only when backend, model-config, and model-auth are all supplied. Without them the action keeps the context-bundle-only behavior and does not index. Configured reviews index by default; set indexing: disabled for file-only review.

Publication ​

When github-token is supplied together with review execution, the action publishes the review to GitHub after writing the artifacts:

  • One review per file with validated findings, bound to the reviewed head through commit_id, with one inline comment per finding. Publication runs as its own step with a freshly minted token after the review completes. Each comment carries the issue explanation, an apply-able suggestion block when the model proposed a concrete change, and the fix prompt for a coding agent.
  • One managed summary comment with run counts and per-file outcomes, updated in place on re-runs. A "review in progress" body is published when the run starts — the review runs one prompt per reviewed file and can take a while — and is replaced by the run summary (or the failure state) when the run completes. Parallel completion never changes manifest-order artifacts, synthesis, or publication. Publication context (repository, pull request, head) arrives together with the token; a partial selection fails validation.
  • Every managed object carries a machine-readable marker. Updating or creating one requires both the marker and the expected author, so the action never touches another author's content. The author is resolved from the token: a PAT through GET /user; a GitHub App installation token has no user behind /user, so the publisher learns its actor from the first object the token creates (authoritative response). Across runs, actor-unavailable fallback recognizes only the exact running, failed, or completed summary headings and the ## Redline review: <path> file-review heading. It adopts one matching object in place, fails closed on ambiguity, and never touches a copied marker under an unrecognized heading. An explicit bot login (botLogin) remains an optional identity override.
  • Before publishing, the action re-reads the pull request head and aborts when the PR has moved past the reviewed commit.
  • Caps bound publication: at most 25 file reviews and 100 inline comments per run. Files and findings beyond the caps appear only in the summary.
  • Per-file publication failures never abort the run; failures are counted and reported in the summary. The action fails only when publication was requested and no requested file review succeeded.

Re-runs on the same head are idempotent: an existing actor-owned review with the same marker is skipped, and the summary is updated in place. Reviews on earlier heads are outdated automatically by GitHub.

Pipeline ​

  1. Validate action inputs — the event must be a pull_request with full base and head commit identifiers; the artifact settings and the all-or-nothing review-input rule are enforced.
  2. Set up and check trusted TypeScript — the selected Redline source runtime is installed (Node 24 by default or Bun 1.4.4), and the trusted source entrypoints are checked for presence. The review action does not run Corepack, install project dependencies, or type-check on the review critical path; strict tsc --noEmit remains a required CI gate. Pull request code is never installed, checked, or executed. The selector is not applied to harness commands. GitNexus separately installs its fixed Node 24 provider runtime.
  3. Generate Redline App token for review start — token 1, used by the announce and failure-notification steps; the publication token falls back to github-token when the App inputs are unset.
  4. Validate action inputs with trusted TypeScript — the review CLI runs --validate-only against the REDLINE_* environment contract; invalid optional inputs fail even in context-only mode.
  5. Restore validated per-file records — a PR-scoped GitHub Actions cache is restored into a dedicated directory. Availability is optional; missing or invalid cache data never changes correctness.
  6. Fetch pull request commits as data — base and head commits are fetched as Git objects and verified.
  7. Build bounded code index — for configured reviews with indexing enabled, the root action invokes $/github/code-index. GitHub resolves this self-repository reference at the root action's exact running commit. The child action exports the head as data, restores or builds the selected provider's bounded base-revision database, and writes provider-neutral code-index/code-context.json.
  8. Build review context bundle — the selected runtime executes src/context-bundle.ts directly to produce the manifest, diffs, base files, and a source-at-head export; a PR requirements file is folded in when present. Eligibility uses only strict trusted-workflow JSON or .redline/review-eligibility.json read from the exact base Git revision. Every exclusion carries a reason; pull-request head policy cannot suppress its own review.
  9. Upload review context artifact — <artifact-name>-context with the bounded code-context.json when generated, source-at-head/, and review/.
  10. Ensure harness binary — installs the selected harness's fixed npm package when review execution is enabled and the binary is not already present (pi or opencode; echo needs nothing). When Bun runs Redline source, a separate pinned Node 24 runtime is installed only for these Node-based harness commands. The runtime selector never changes the harness runtime. This is trusted workflow tooling, never pull request code.
  11. Announce review start — publishes the "review in progress" comment (continue-on-error; a failed notification never blocks the review). Token 1 covers this and the failure notification.
  12. Run harness review — token-free by design: the review process carries no publication credential. Before creating the worker queue, the CLI fingerprints every review-affecting input and restores only matching validated clean or findings records. Cached findings are remapped to the current base/head and revalidated against the current authoritative diff, source, and graph facts. Misses enter the bounded worker pool. Parallel runs schedule larger diffs first, isolate every Pi/OpenCode invocation, and restore manifest order before synthesis and publication. Each call receives the lesser of timeout and the remaining run-timeout; expiry produces explicit file omissions. review-concurrency: 1 keeps manifest traversal. Candidate-verification benchmark mode remains serial while it uses the shared follow-up budget.
  13. Save validated per-file records — eligible records are written incrementally and the PR-scoped cache is saved with a unique run key under always(), so completed work can survive later failures or cancellation when GitHub permits the save step to run.
  14. Generate Redline App token for publication — token 2, minted after the review completes; it covers only the publication itself, so the token lifetime never bounds the review duration.
  15. Publish review — --publish-only re-reads the written records and summary from the output directory and publishes them (stale-head guard, run-to-head match, caps, per-file failure accounting).
  16. Notify review failure — when the harness review step failed, replaces the "review in progress" comment with the failure state (continue-on-error); prefers the fresh publication token when one was minted.
  17. Upload review output artifact — <artifact-name>-reviews with the per-file JSON and Markdown records and the run summary.

Boundaries ​

  • Pull request content is untrusted data. The harness receives it only inside a delimited context block with an explicit untrusted-data framing; it never alters the fixed policy. Review eligibility is selected only by trusted workflow input or the exact-base policy file, never by the pull-request head.
  • The harness runs with tools disabled and a constructed environment; no GitHub token or ambient credentials reach it. Every concurrent Pi/OpenCode call gets separate generated configuration, prompt, home, and state paths. The publication token is consumed only by the publication layer after the review artifacts are written.
  • Model output must validate against the authoritative diff — path, side, line, and byte-identical evidence — or the finding is rejected. Persisted reasons and raw model output are redacted against the selected credential before artifacts are written.
  • Restored review records are untrusted. Redline enforces cache version, namespace, file-name/path identity, SHA-256 integrity, schema, entry count, per-entry bytes, and total bytes. A semantic match includes the fixed policies and schemas, harness/model configuration, finding scope, timeout, diff, bounded revision-pinned source context, requirements, and source-resolved indexed context. Omissions and incomplete verification are never cached. A mismatch or validation failure becomes a normal model execution.
  • Indexed relationships only select candidates. Every injected span carries its path, line range, repository revision, provider/version, selection reason, and coverage status, and is re-resolved from the captured exact-head source with symlink and strict UTF-8 checks. Source files are capped at 2 MiB, selected content at 24 KiB per changed file and 48 KiB per run. Indexed context can never provide the published finding location.
  • Internal action composition uses GitHub.com's $/ self-repository reference. GitHub Enterprise Server does not support this syntax; Forgejo and Gitea remain separate future entry points.
  • In context-only mode (review inputs empty) the action does not index and uploads only <artifact-name>-context; the <artifact-name>-reviews artifact is produced only when review execution is enabled.
  • Release tags contain the exact reviewed TypeScript source. The action executes only its trusted action revision; pull request source remains data and is never loaded as code.

See runnable review configuration for the environment contract, harness executor for harness specifics, and review output for the record schema.
